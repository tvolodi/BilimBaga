## 1. Context

`bilimbaga-test.ai-dala.com` (hetzner-prod, `/opt/apps/bilimbaga-test`, containers `bilimbaga-test-*`, `deploy/docker-compose.test.yml`, `deploy/redeploy-test.sh`) was treated by the swarm as a test sandbox: UAT, seed scripts and the FR-BB65 evidence plan (k6 with `DISABLE_RATE_LIMIT=true`) could target it. The user has now decided it is a **customer demo**, i.e. production-class. It has no scheduled DB backup (retro-001, retro-002 carry-over). `swarm/PROTOCOL.md` section 8 and `swarm/roles/infra.md` still describe it as a test environment.

## 2. Decision

1. `bilimbaga-test.ai-dala.com` is **production-class**. It is no longer a swarm test target. Its name is historical; renaming is out of scope.
2. The swarm gets a separate **QA instance**: host `bilimbaga-qa.ai-dala.com`, compose project `bilimbaga-qa`, `/opt/apps/bilimbaga-qa`, own DB volume, own host port, own vhost and DNS record, `PUBLIC_APP_URL=https://bilimbaga-qa.ai-dala.com`. No Keycloak realm is involved: BilimBaga uses its own JWT auth (the `bilimbaga` realm name belongs to Letflow).
3. Until QA exists the swarm uses the **local stack only** (`make dev`; UAT owns the stack lock).
4. Production-class actions are reserved for the user (global rule). Infra builds QA only after the user confirms scope (DNS, host resources). Issue #106 stays `status:blocked` (needs user) until then.

## 4. Rules for swarm roles

Against the prod-class instance, **no** role may run: automated tests (Playwright, e2e, integration), UAT scenarios, seed scripts (`seed-test-env.ts` etc.), load tests (k6), `DISABLE_RATE_LIMIT=true`, destructive DB operations (DROP/TRUNCATE/DELETE, migrate down, volume removal), account creation or password resets, or ad-hoc config edits.

- Deployment to it: only the user, or Infra on explicit user approval for that deploy (issue labelled `status:blocked`, "needs user approval"). Infra's default tick on it is a read-only health check.
- Before any approved change: a verified DB backup (dump stored off the container volume) must exist; Infra records its path in the issue.
- A rollback plan is stated before deploy.
- UAT, Dev and E2E roles use the local stack until QA exists, then QA for deployed-build checks. Scenarios declare `Target: local | qa`.
- Any issue needing the prod-class instance is labelled `status:blocked` and reported to the Supervisor.

## 5. Configuration requirements

| Setting | Local | QA | Prod-class |
|---------|-------|----|-----------|
| `PUBLIC_APP_URL` | `http://localhost:5173` | `https://bilimbaga-qa.ai-dala.com` | `https://bilimbaga-test.ai-dala.com` (QR codes must not point at QA/localhost) |
| `SMTP_*` | Mailhog (`HOST_MAILHOG_SMTP_PORT`) | Mailhog/sink or empty; must not reach real recipients | Real relay configured deliberately; `SMTP_FROM` a real sender |
| `DISABLE_RATE_LIMIT` | allowed for perf runs | allowed for the run only, restored after | unset/false at all times |
| `JWT_SECRET` | dev default allowed | unique random >= 32 chars, differs from prod-class | unique random >= 32 chars, never shared, not the `.env.example` value |
| Seed/default accounts (`admin@bilimbaga.local`, e2e seed users) | allowed | allowed | must not exist, or credentials rotated to unique strong values |
| Backups | none | none required | scheduled DB backup + tested restore |

Each environment has its own DB volume, secrets and `.env`; secrets are never committed.
