# FR-BB319 — Anti-Cheat Event Hygiene: Single Report per Incident, Auto-Submit Only on Tab Switch, Fullscreen Exit

## Description
FR-BB38 (server) and FR-BB314 AC-7 (client) shipped tab-switch reporting, but the combination misbehaves in three ways, all verified on `main`:

1. **Double reporting.** `useTabSwitchDetection` listens to `visibilitychange` (reports `tab_switch` when hidden) AND `window` `blur` (always reports `blur`). A real tab switch fires both, so one incident writes two `tab_switch_events` rows, raises `event_count` by 2 and can raise the warn modal twice.
2. **Auto-submit on a weak signal.** `ReportEvent` applies the exam's `on_tab_switch` policy to every event type. With policy `submit`, a bare `blur` (a click outside the window, DevTools, an OS notification, a password-manager popup, an assistive-technology focus move) auto-submits and grades the candidate's exam. A false positive here ends the exam.
3. **`fullscreen_exit` is never sent.** The type is accepted by the API and typed on the client, but nothing requests fullscreen or listens for `fullscreenchange`, so the roadmap's third event type does not exist in practice.

This requirement fixes the three problems with the smallest change: **no migration and no new exam setting**. The request body and response envelope of `POST /portal/sessions/:id/events` are unchanged (no new API contract).

**Known limitation kept on purpose:** `tab_switch_events` stores `id, session_id, occurred_at, action_taken` only; the event type is NOT persisted (`InsertTabSwitchEvent` ignores its `eventType` argument). After this change a `blur` and a `tab_switch` under policy `warn` both store `action_taken = 'warn'` and cannot be told apart in the database. Persisting the type needs a numbered migration and is listed under Out of Scope.

## Decisions (BA, 2026-10-09)
- **D-1 One signal, one report.** One physical focus loss produces at most one reported event per signal source, and the same loss is never reported by both sources (ordered rules in AC-4 to AC-7). A `tab_switch` that follows an already reported `blur` (for example the browser later marks the covered window hidden) is a second, deliberate event: the candidate really left the tab.
- **D-2 Only `tab_switch` can auto-submit.** The exam policy `on_tab_switch = 'submit'` auto-submits on `tab_switch` only. For `blur` and `fullscreen_exit` the effective policy is capped at `warn` (`log` stays `log`, `warn` stays `warn`, `submit` becomes `warn`). The cap is applied on the server; the client never decides.
- **D-3 Fullscreen is requested, not enforced.** The candidate's own click on the exam start confirmation requests fullscreen (a user gesture, so browsers allow it). Failure or an unsupported browser (for example iOS Safari) is silent: the exam runs without fullscreen and no `fullscreen_exit` is ever sent. After leaving fullscreen once, the app does not force it again except through the warn modal's "Return to full screen" button.
- **D-4 No dedup on the server.** FR-BB38 AC-9 stays: every call records a row. Hygiene is done on the client (D-1) and by the capped policy on the server (D-2).
- **D-5 No migration.** The event type is not persisted (see the limitation above); tests assert the type on the client request and `action_taken` in backend tests.

## Acceptance Criteria

### Server
- [ ] AC-1: With `exam.on_tab_switch = 'submit'` an event of type `blur` or `fullscreen_exit` does NOT submit the session. The response is `200` with `{ warn: true, event_count: N }` and contains no `session_id`, `status`, `score_pct` or `passed` field. One row is inserted with `action_taken = 'warn'`. An event of type `tab_switch` still auto-submits exactly as FR-BB38 AC-2.
- [ ] AC-2: With `on_tab_switch = 'warn'` or `'log'` the behaviour of all three types is unchanged from FR-BB38 AC-3 and AC-4, and `action_taken` equals the exam policy.
- [ ] AC-3: The `action_taken` stored for an event is the EFFECTIVE policy (AC-1, AC-2), not the raw exam policy. FR-BB38 AC-10 is amended accordingly. (Type is not stored; see the limitation.)

### Client detection (`frontend/src/hooks/useTabSwitchDetection.ts`)
Signature becomes `useTabSwitchDetection(sessionId, onWarn, onAutoSubmit, enabled = true)`; `ExamLayout` passes `enabled = session.status === 'in_progress'`. When `enabled` is false the hook adds no listeners; when it turns false or the component unmounts all listeners (`visibilitychange`, `blur`, `focus`, `fullscreenchange`) and the pending blur timer are removed.
- [ ] AC-4: **Ordered rule for a tab switch.** On `visibilitychange` with `document.visibilityState === 'hidden'` the hook sends `{type:'tab_switch'}` immediately and records `lastTabSwitchAt = now`. It sets `hiddenReported = true`. A further `tab_switch` is sent only after the document has been `'visible'` again (`hiddenReported` is cleared on `visible`), so repeated hidden notifications without a return never send a second event.
- [ ] AC-5: **Ordered rule for blur.** On `window` `blur` the hook starts a 300 ms timer (clears any earlier one). When it fires it sends nothing if `document.visibilityState === 'hidden'`, or `hiddenReported` is true, or `blurReported` is true (a `tab_switch` sets both flags, so a blur that came before the hidden notification is also dropped). Otherwise it sends `{type:'blur'}` once and sets `blurReported = true`. This covers `blur` firing before or after `visibilitychange`.
- [ ] AC-6: `blurReported` is cleared by a `window` `focus` event OR by `visibilitychange` to `'visible'` (a browser may return to the tab without a window `focus`). A `tab_switch` also sets `blurReported = true`, so the `blur` that accompanies a tab switch is never sent; the next `focus` or `visible` clears it.
- [ ] AC-7: **Fullscreen exit.** The hook owns the fullscreen state and returns `{ enteredFullscreen }` to `ExamLayout`. `enteredFullscreen` starts as `document.fullscreenElement !== null` at mount and becomes true at the first `fullscreenchange` with a non-null `document.fullscreenElement` (so a slow `requestFullscreen()` transition is still caught). While `enabled`, on a `fullscreenchange` with `document.fullscreenElement === null` and `enteredFullscreen` true, the hook starts its OWN 300 ms timer (separate from the blur timer, so the two never cancel each other); when it fires it sends `{type:'fullscreen_exit'}` once for that exit and handles the response like other events (warn modal on `warn: true`), unless `document.visibilityState === 'hidden'`, or `hiddenReported` is true (a minimise or Esc that also hid the tab is reported as `tab_switch` only), or `blurReported` is true (Alt-Tab out of fullscreen fires both `blur` and the fullscreen exit: one incident, one report). A sent `fullscreen_exit` sets `blurReported = true`, so a following `blur` is dropped. An exit is reported at most once per transition of `document.fullscreenElement` to null: a per-exit flag `exitReported` is set when it is sent and cleared by the next `fullscreenchange` with a non-null element (re-entry), so each later exit reports once. After a page reload or session resume fullscreen is gone and `enteredFullscreen` is false until the user enters it again, so no `fullscreen_exit` is sent.

### Fullscreen request and modal
- [ ] AC-8: In `frontend/src/pages/EmployeePortal/index.tsx` `handleConfirm` (the exam start confirmation click) calls `document.documentElement.requestFullscreen()` synchronously as its first statement, before `createSession.mutate(...)` (a user gesture is required; an async gap would lose it). A missing API or a rejected promise is caught and ignored: no toast, no event, no console error. The client-side navigation to `/portal/sessions/:id` keeps fullscreen. No other code path requests fullscreen (not on reload, not on resume).
- [ ] AC-9: `TabSwitchWarningModal` (`frontend/src/pages/ExamTaking/TabSwitchWarningModal.tsx`) gets props `count: number`, `canReturnFullscreen: boolean`, `onReturnFullscreen: () => void`. It shows the running count from the server `event_count` (the count line is hidden when `count` is below 1, because the server omits `event_count` for the first `log` events and for submitted sessions) and, when `canReturnFullscreen` is true (that is `enteredFullscreen` from the hook and `document.fullscreenElement === null`), a "Return to full screen" button that calls `requestFullscreen()` (errors ignored) and closes the modal. The existing close button stays; closing without it keeps the exam running. Both usages in `ExamLayout.tsx` (about lines 304 and 400) pass the new props; `count` is stored from the last event response in `ExamLayout` state.
- [ ] AC-10: New i18n keys in `frontend/src/locales/kk.json`, `ru.json`, `en.json` under `exam.taking.tabswitch`: `count` ("Violations recorded: {{count}}") and `returnFullscreen` ("Return to full screen"). No hardcoded strings; `npm run check:i18n` stays green.

## Technical Notes
- Server change is in `backend/internal/sessions/service.go` `ReportEvent`: `effective := cfg.OnTabSwitch`; if `input.Type != "tab_switch"` and `effective == "submit"` then `effective = "warn"`; pass `effective` to `InsertTabSwitchEvent` and switch on `effective`. No migration; `action_taken` already stores text. The handler and request validation are unchanged.
- Client calls go through the existing React Query mutation `useReportEvent` (no raw `fetch`). `fullscreenchange`, `focus` and `blur` listeners belong to the same `useEffect` as the existing ones, depending on `sessionId` and `enabled` ONLY. `hiddenReported`, `blurReported`, `exitReported`, `lastTabSwitchAt` and the fullscreen flag read by the listeners live in refs (a state dependency would re-run the effect and drop pending timers); the value returned to `ExamLayout` as `enteredFullscreen` and as the modal's `canReturnFullscreen` is state updated from the same `fullscreenchange` handler so the modal re-renders.
- Fullscreen needs a user gesture, hence AC-8 inside the click handler. The resume path (`GET /portal/sessions/:id`) never requests fullscreen.
- The count shown to the candidate is the server `event_count`; with D-1 one incident counts once.
- Results and analytics that list tab-switch events keep reading `tab_switch_events`; the `action_taken` value set gains no new values (`log`, `warn`, `submit`).

## Out of Scope
- Persisting the event type in `tab_switch_events` (needs a new numbered migration; possible follow-up when results or analytics should show the type).
- A new exam setting to choose the policy per event type, or to require fullscreen (possible follow-up if the customer wants stricter proctoring).
- Server-side deduplication or rate limits on events (FR-BB38 AC-9 unchanged).
- Webcam, screen recording or other proctoring.
- Special handling of screen-reader focus moves (D-1 and D-2 already stop a stray `blur` from submitting).

## Test Strategy
See AC-11 to AC-13. A UAT scenario is authored after validation: run an exam under each policy, switch tabs, click outside the window, exit fullscreen, and check row counts, the warn modal and the submit outcome.
