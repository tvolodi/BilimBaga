## Description
Since #528 an exam with short-text answers is submitted at once and graded afterwards: by a background job (AI on, answers eligible) or by an examiner. The employee is left without a state to look at: the result page never refreshes and promises "manual grading", the portal card goes back to "not started", the attempt is not counted while it waits, the history list hides the session, and the result mail points to an API path that has no token when opened from a mail client. This requirement defines what the employee sees, and what the system counts, from submit until the result is final. It changes no grading rule (FR-BB311, FR-BB73) and no score rule.

## Acceptance Criteria
- [ ] AC-1: Attempt counting. A session with `status = 'grading_pending'` counts as a used attempt everywhere `submitted` and `auto_submitted` count for the employee: the start-attempt check (`CountFinishedSessions`, `repository.go`), the count and the rows of `GetExamHistory` and of `GetMyResults` (FR-BB46), `attempts_used` from `computeStatus` and the `AttemptHistory` filter of `GetMyExam` in `portal/service.go`. Report and analytics queries are out of scope (they already include or deliberately exclude pending sessions, FR-BB52). Order of checks in `CreateSession`: first a session of that user and exam in `grading_pending` (409 `GRADING_PENDING`, AC-3), then the exhausted-attempts check with its existing error. A test covers each counting place listed, and a start with `max_attempts = 1` and only a pending session returns `GRADING_PENDING`, with only finished sessions returns the exhausted-attempts error.
- [ ] AC-2: Portal status. `user_status` gains the value `grading_pending`. Priority in `computeStatus`: `passed`, `in_progress`, `grading_pending`, `expired`, `failed`, `not_started`. `grading_pending` is returned when no session passed, none is open, and at least one session is `grading_pending`. A pending session never counts as passed: `computeStatus` ignores the stored `passed` of a session whose status is `grading_pending` (see AC-13). When that session is finalised the status becomes `passed` or `failed` by the existing rules. Table-driven unit tests cover the priority, including a passed session next to a pending one, a pending session whose stored `passed` is true, and an expired deadline with a pending session. The TypeScript `UserStatus` type (`frontend/src/api/portal.ts`) and `STATUS_VARIANT` in `ExamCard.tsx` gain the member.
- [ ] AC-3: Portal card and start. `ExamCard` shows a badge `portal.card.status.grading_pending` (variant `secondary`) and a line with the submit time (`pending_submitted_at`) for `grading_pending`; the Start and Retake buttons are not rendered; a link `portal.card.cta.viewStatus` goes to `/portal/sessions/{pending_session_id}/result`. The API item carries `pending_session_id` (nullable string, the newest `grading_pending` session) and `pending_submitted_at` (nullable UTC ISO 8601 of that session's `submitted_at`). No retake is offered while a session waits, even when attempts remain, and the API enforces it: `POST /portal/exams/:id/start` answers 409 `GRADING_PENDING` while a session of that user and exam is `grading_pending`.
- [ ] AC-4: Result API. For a session in `grading_pending`, `GET /portal/sessions/:id/result` returns 200 with `status = "grading_pending"`, `score_pct = null`, `passed = false` (the stored values are ignored, AC-13), and the new fields `pending_question_count` (int, answers still `pending_manual`), `total_gradable_count` (int, all short-text answers of the session) and `grading_expected_by` (`"ai"` or `"examiner"`). `grading_expected_by` is `"ai"` when at least one pending answer is eligible for the AI job and the AI result will be its grade rather than a suggestion. Job eligibility is one shared per-session function (a query that both `aigradejob.go` and `buildSessionResult` call; the job's batch query is refactored to use the same conditions, not copied): AI provider configured, `AI_GRADING_DAILY_LIMIT` not 0 and the count of `ai_usage_log` rows of feature `short_text_grading` in the last 24 h below it, question `auto_grade` with a non-empty model answer, answer text not null, session submitted within the last 24 h, `ai_grade_attempts < 2`. The result service receives the AI configuration by injection. Job eligibility is what the job selects. Once FR-BB73 revision 2 (#534) is implemented, the job also selects `suggest` exams and requires `ai_suggested_score_pct IS NULL`, but `grading_expected_by` is `"ai"` only for eligible answers of an exam with `ai_grading_mode = 'auto'` and no stored suggestion (FR-BB73 AC-11 adds both clauses; until then neither is part of the predicate). Otherwise `"examiner"`. The fields are always present: for a final session `pending_question_count` is 0 and `grading_expected_by` is `null`. The admin result (`GetAdminSessionResult`) returns the same new fields but keeps the stored partial `score_pct` and `passed`, which examiners need; AC-13 applies to employee-facing reads only.
- [ ] AC-5: Result page notice. When `status = 'grading_pending'` the page shows, in place of dial and banner, a notice with the submit time and the count "N of M answers are still being checked". The text comes from `result.pending_ai` (AI: "Your answers are being checked automatically. This usually takes a few minutes.") or `result.pending_examiner` ("Your answers are waiting for an examiner. You will get an email when the result is ready."), chosen by `grading_expected_by`. The old key `result.pending_grading` is removed. Certificate, retake and breakdown actions stay hidden (FR-BB45 AC-8 is replaced by this AC).
- [ ] AC-6: Polling. While the displayed status is `grading_pending`, `useSessionResult` (today `staleTime: Infinity`) refetches every 10 seconds (`refetchInterval` as a function that returns `false` for any other status and `staleTime` lowered for that case), does not poll in a hidden tab, and stops after 15 minutes of polling. After that stop the page shows `result.pending_stopped` ("We stopped checking automatically. Refresh to see the latest state.") and a Refresh button that refetches once and re-arms the 15 minutes. Tests with fake timers: polls at 10 s, stops on final status, stops at 15 min, Refresh re-arms.
- [ ] AC-7: Transition. When a poll returns a final status the page renders the normal result (dial, banner, actions per FR-BB45 AC-1 to AC-7), announces `result.ready` through an `aria-live="polite"` region, and invalidates the query keys used in code today: the portal exams prefix `['portal','exams']` (list and detail), `['my-results']`, `['exam-history', examId]` (read by the exam-level redirect of AC-14) and the key of `useSessionResult` itself (`['session-result', id]`). The dev confirms the exact keys in `frontend/src/api/portal.ts` and `sessions.ts`; a test asserts the invalidation calls.
- [ ] AC-8: Pending marker per question. `QuestionBreakdownItem` gains `grading_status` (`graded` or `pending_manual`). When the breakdown is shown (the exam allows it, FR-BB45 AC-5), a question with `pending_manual` shows the text `result.question_pending` ("Awaiting grading") in the points cell and no correct answer or explanation; graded questions render as before. The breakdown is returned for a pending session only when the exam allows it; this AC does not widen what an employee may see. Points of graded questions: while the session is `grading_pending`, a graded question shows its points under the same rule as AC-5 (`show_answers_mode != 'never'`; that setting also exposes correct answers and explanations, and the code does not distinguish its other values), so an employee may add up the points of auto-graded questions; accepted, it is the exam's setting. The page shows no total, no percentage and no pass or fail until the result is final (AC-13 is about those fields, not about per-question points).
- [ ] AC-9: Submitted mail. One email `exam_submitted` is queued to the employee in their preferred locale (kk, ru, en) when a session first moves to `grading_pending`: exam title, submit time, and a link `{PUBLIC_APP_URL}/portal/sessions/{id}/result`. Three paths make that transition: the manual submit, the auto-submit that `ReportEvent` triggers, and the expiry job (`autojob.go`). `SubmitSession` and `AutoSubmitSession` gain an explicit `transitioned bool` result that is true only for the call that changed the status (a replay returns false); the expiry job uses its existing `WHERE status = 'in_progress'` and `rowsAffected` guard. The mail is sent only when `transitioned` is true, so exactly one per session. It is sent only when SMTP is configured, like the other mails, and a send failure never fails the submit. The AI job and manual grading send no `exam_submitted` mail. Tests: manual submit twice sends one; auto-submit after a manual submit sends none; the expiry job sends one.
- [ ] AC-10: Result mails. `exam_passed` and `exam_failed` are sent only when a session reaches a final result (status `submitted` or `auto_submitted`, i.e. neither `in_progress` nor `grading_pending`), never at the submit of a `grading_pending` session: the trigger at `sessions/service.go` (today `result.Passed != nil`) is guarded by `result.Status != "grading_pending"`, with a test that a submit with a short-text answer sends no `exam_passed` or `exam_failed`. Both mails link to `{PUBLIC_APP_URL}/portal/sessions/{id}/result`, an SPA route; `CertDownloadLink` is removed from the template because the certificate is downloaded with a token from that page (FR-BB45 AC-6). A signed-out reader who opens the link is sent to login and returned to that path afterwards (the route guard `RequireRole` passes `state.from` and `LoginPage` uses `returnPath`; a test covers the return for `/portal/sessions/:id/result`).
- [ ] AC-11: i18n and design. Every new string (AC-3, AC-5, AC-6, AC-7, AC-8 and the mail templates of AC-9) exists in `frontend/src/locales/{kk,ru,en}.json` (card keys under `portal.card.status.*` and `portal.card.cta.*`, result keys under `result.*`) or in the three mail template locales; `npm run check:i18n` and `npm run check:design` stay green (tokens only, no raw palette classes).
- [ ] AC-12: UAT scenario. `docs/uat-scenarios/grading-pending-experience-<date>.md` covers: auto-submit by tab switch and by expiry with no short-text answer sends one result mail; submit with a short-text answer and AI off (examiner notice, the page shows the pending state until an examiner grades, then flips to the result within 10 s), submit with AI on (AI notice, result within the job time), portal card state, attempt cap with `max_attempts = 1` (409 `GRADING_PENDING`), mail at submit and no result mail until final, mail links and login return, hidden-tab pause.
- [ ] AC-13: Pending sessions carry no result for the employee. The submit path stores a partial `score_pct` and `passed` for a `grading_pending` session today (`grading.go`). Wherever an employee-facing read returns them, a `grading_pending` session returns `score_pct = null`, `passed = false`, `per_section_scores = []` and no certificate: `buildSessionResult` for the employee, the history rows of `GetExamHistory`, the rows of `GetMyResults` (no `COALESCE(score_pct, 0)` for a pending row, `certificate_available` false) and the portal status. The TypeScript types (`score_pct: number | null` in `frontend/src/api/sessions.ts`) and the components that render them show the label `portal.card.status.grading_pending` instead of a number. The stored values stay as the grading engine writes them (finalisation overwrites them); this AC changes employee reads only.
- [ ] AC-14: Exam-level result redirect. `/portal/exams/:id/result` (`ExamResultRedirectPage.tsx`) opens the `grading_pending` session when one exists, otherwise the newest attempt. Today it reads `useExamHistory` with `per_page=1` in ascending `started_at` order and so opens the oldest attempt; the page requests `per_page=100` (a cap above any `max_attempts`) and picks the session by this rule from the rows, so the query key payload gains the page size and the invalidation of AC-7 keeps matching by the `['exam-history', examId]` prefix. A test covers three attempts and one pending attempt that is not the oldest.
- [ ] AC-15: Result mail on automatic submit (#551). A session that ends by automatic submit and reaches a final result at once (no short-text answer to grade; status `auto_submitted`) sends exactly one `exam_passed` or `exam_failed` mail, with the same templates and the same link as a manual submit (AC-10). Two paths end a session automatically: a tab-switch or blur policy `submit` through `ReportEvent`, and the expiry job (`autojob.go`); both are covered. The mail is sent by the call that performed the transition (`transitioned`, AC-9), so a replay, a second event after the session ended, or an auto-submit of a session that is already final sends nothing. An automatic submit that leads to `grading_pending` sends `exam_submitted` (AC-9) and the result mail at finalisation, as for a manual submit. With SMTP unconfigured nothing fails. Tests: each of the two paths sends one result mail with the right template for pass and for fail; an auto-submit after a manual submit sends none; the expiry job run twice sends one. Seam: `ReportEvent` mails when the transition is the winning call and the status is `auto_submitted`; the expiry job takes a second callback `onFinal(sessionID)`, called after commit when the session has no short-text question (the existing `onGradingPending` stays for the other case).

## Technical Specification

### Database Schema
None. `pending_session_id` and the counts are computed from `exam_sessions` and `session_question_scores`; no migration.

### API Contract
- `GET /api/v1/portal/exams` and `GET /api/v1/portal/exams/:id`: item gains `pending_session_id` (string or null) and `pending_submitted_at` (string or null); `user_status` gains `grading_pending`; `attempts_used` counts `grading_pending`.
- `GET /api/v1/portal/sessions/:id/result`: fields of AC-4. Errors unchanged.
- `QuestionBreakdownItem` gains `grading_status`. `SubmitSessionResponse` is unchanged for the client; `transitioned` is internal to the repository result.
- `POST /api/v1/portal/exams/:id/start`: new error 409 `GRADING_PENDING` (AC-1, AC-3).
- No new endpoint. All responses keep the `{data, error}` envelope.

### Go Implementation Notes
- `backend/internal/sessions/repository.go`: `CountFinishedSessions`, the history and `GetMyResults` queries (`status IN ('submitted','auto_submitted')` becomes `IN ('submitted','auto_submitted','grading_pending')`). Check every other consumer of those queries (analytics already includes `grading_pending`).
- `backend/internal/portal/service.go` `computeStatus` and `model.go` (`UserStatusGradingPending`); `portal/repository.go` selects `status` already.
- `backend/internal/sessions/service.go` `buildSessionResult`: counts from `session_question_scores`; `grading_expected_by` from the job's eligibility predicate, shared with `aigradejob.go` so the two cannot drift.
- `backend/internal/email/service.go`: the email `Config` already has `PublicAppURL` (passed from `main.go`); links in `exam_submitted`, `exam_passed` and `exam_failed` are built from it, not from `APIBaseURL`. Template `exam_submitted`, triggered from the submit path only when the repository reports a first (non-replay) transition to `grading_pending`; no new column.
- Frontend: `frontend/src/api/sessions.ts` (`useSessionResult`, `SessionHistoryItem`), `frontend/src/pages/ResultPage.tsx`, `frontend/src/pages/EmployeePortal/ExamCard.tsx`, `frontend/src/api/portal.ts` types. The exam-level result redirect is AC-14.

## Out of Scope
- Push or in-app notifications and websockets; polling is enough at this size.
- Who may grade and how far an AI score is trusted: FR-BB73 amendment (#534).
- Changing grading rules, certificate rules or the score.
- An admin view of the wait (the grading queue already lists `grading_pending`).
