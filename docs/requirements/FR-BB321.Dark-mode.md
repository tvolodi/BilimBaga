## Description
`frontend/src/index.css` already defines the dark tokens under a `.dark` class on `<html>` (it uses no `color-scheme` property yet), but nothing in the app sets that class and there is no switch, so users cannot reach dark mode. This requirement adds it: a three-way preference (light, dark, system), a switch on every layout, no flash of the wrong theme on load, theme-aware charts, logo and tenant colours, and contrast checks of the key pages in both themes. The design system (`docs/design-system/foundations.md`) already specifies the dark values.

## Decisions (BA, 2026-10-10)
- **D-1 Preference values:** `light`, `dark`, `system`. Default `system` (follows `prefers-color-scheme` and later OS changes while the page is open).
- **D-2 Stored on the device, not on the account:** `localStorage` key `bb-theme`. No migration, no API change. Per-account sync is a possible follow-up (the locale is account-bound, FR-BB116; the theme deliberately is not).
- **D-3 Mechanism:** the existing `class="dark"` on `<html>` plus the CSS `color-scheme` property (`light` or `dark`) set on `<html>` so native controls and scrollbars follow.
- **D-4 No flash:** a blocking classic script `frontend/public/theme-init.js`, referenced from `<head>` of `frontend/index.html` before the app, sets the class and `color-scheme` before first paint. It is a same-origin file, not an inline script, so it keeps working if the CSP drops `'unsafe-inline'` (FR-BB64; today `script-src 'self' 'unsafe-inline'`).
- **D-5 Exam mode:** no switch in the exam bar (exam mode has no navigation except the exam bar), but the stored theme applies on the exam screen.
- **D-6 Tenant colours are applied unchanged in both themes** (inline `style` overrides on `<html>` beat the `.dark` block); only the foreground colour on the tenant primary is computed. A tenant primary that is itself dark has no contrast guarantee against the dark page background (tenant colour validation is out of scope here, as in FR-BB320).
- **D-7 The result screen** renders inside `PortalLayout` and so shows the toggle; D-5 excludes only the exam bar and `ExamLayout`.

## Acceptance Criteria
- [ ] AC-1: `frontend/src/components/ThemeProvider.tsx` exposes `{ preference, resolved, setPreference }` through a context and a `useTheme()` hook. `preference` is `light | dark | system`; `resolved` is `light | dark`. On mount it reads `localStorage['bb-theme']`; a missing, unparsable or unknown value is treated as `system`; every `localStorage` access is in try/catch (private mode, blocked storage) and the provider works without storage. The context has a default value (`preference: 'system'`, `resolved: 'light'`, `setPreference` a no-op) so `useTheme()` never throws outside the provider; existing tests that render `TenantLogo`, `LoginPage` or `BrandingPreview` without a provider keep passing. `setPreference` stores the value (removes the key for `system`) and applies it.
- [ ] AC-2: Applying a theme adds or removes `class="dark"` on `document.documentElement` and sets `document.documentElement.style.colorScheme` to `light` or `dark`; this happens synchronously inside `setPreference` and the `matchMedia` handler BEFORE the React state is updated, so any component that reads CSS variables after a state change sees the new theme. With `system`, the provider subscribes to `window.matchMedia('(prefers-color-scheme: dark)')` change events and re-applies; the subscription is removed on unmount.
- [ ] AC-3: `frontend/public/theme-init.js` (classic script, not a module, no requests, wrapped in try/catch, at most 30 lines) applies the same rules as AC-1 and AC-2 for the first paint. `frontend/index.html` references it in `<head>` as `<script src="/theme-init.js"></script>` (no `type="module"`; Vite leaves such a tag alone, so the file is neither bundled nor hashed, and serves `public/` at `/` in dev and copies it to `dist/` in the build). A vitest test reads the file text and runs it with `new Function(text)()` in jsdom for: stored `dark`, stored `light`, stored invalid value, storage throwing, OS dark without a stored value, OS light without a stored value (`window.matchMedia` stubbed per test, because jsdom does not implement it).
- [ ] AC-4: nginx serves the script without long caching. Only `deploy/nginx.conf` serves the frontend (it is copied into the image by `deploy/Dockerfile`); add there `location = /theme-init.js { try_files $uri =404; add_header Cache-Control "no-cache" always; ... }` and repeat inside it the five `add_header ... always` lines of the server block (`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy "same-origin"`, `Strict-Transport-Security $hsts`), because `add_header` is not inherited into a location that declares its own. Do NOT change `deploy/nginx/bilimbaga.conf`, `bilimbaga-qa.conf` or `bilimbaga-test.conf`: they are host reverse proxies that pass headers through, and `bilimbaga-test.conf` is the customer demo that swarm roles never touch (CLAUDE.md owner rule).
- [ ] AC-5: `frontend/src/components/ThemeToggle.tsx` is a three-button radio group (`role="radiogroup"` with an accessible name; each button `role="radio"` with `aria-checked`; roving `tabindex` and arrow keys; built on `components/ui/button`) for Light, System, Dark, with lucide icons `Sun`, `Monitor`, `Moon`. No dropdown (the repo has no dropdown-menu primitive). Below 640 px each button is at least 44 px (`min-h-11 min-w-11`).
- [ ] AC-6: Placement. `ThemeProvider` sits in `frontend/src/App.tsx` directly inside `QueryClientProvider`, wrapping `TenantProvider` and `BrowserRouter`, so every route including `/verify/...` follows the theme. The toggle is rendered in: `components/admin/TopBar.tsx` between `LocaleSwitcher` and the profile link; the inline `<nav aria-label="Portal navigation">` of `frontend/src/layouts/PortalLayout.tsx` (this also covers the result screen, D-7); `pages/VerifyCertificatePage.tsx` in its existing top row next to its `LocaleSwitcher` (a fixed corner toggle would overlap it at 375 px); and, for the four auth pages that have no shared layout, a new `components/auth/AuthShell.tsx` that renders a fixed top-end corner toggle (`fixed top-4 end-4`) around its children, used by `pages/auth/LoginPage.tsx`, `ChangePasswordPage.tsx`, `ForgotPasswordPage.tsx` and `ResetPasswordPage.tsx` (their own markup stays inside; check 375 px for overlap with their language selector). `/change-password` is a standalone route under `RequireAuth` with no other layout, so the shell is not doubled there.. It is not rendered in the exam bar or `ExamLayout` (D-5).
- [ ] AC-7: i18n keys in `kk`, `ru`, `en`: `theme.label`, `theme.light`, `theme.system`, `theme.dark`. No hardcoded strings; `npm run check:i18n` stays green.
- [ ] AC-8: Tenant colour foreground. A helper `frontend/src/lib/contrast.ts` (first line `/* design-ok-file: colour maths needs literals */`) exports `readableForeground(hex)` returning `#ffffff` or `#0f1623`, whichever gives the higher WCAG contrast against `hex`; a 3-digit hex is expanded, an invalid value returns `#ffffff`. `TenantProvider` sets `--color-primary`, `--color-accent` (as today) and now also `--color-primary-foreground` from the tenant primary, on `<html>` inline style, in both themes; when the tenant config is absent or has no primary it removes `--color-primary`, `--color-primary-foreground` and the accent; when only the accent is absent it removes only `--color-accent`. Links and focus rings in dark theme keep `--color-text-link` and `--color-ring` from the dark tokens.
- [ ] AC-9: Logo. `TenantLogo` calls `useTheme()`. When `resolved === 'dark'` the `<img>` itself (default mark or tenant upload) gets `bg-white rounded-md p-1` (classes directly on the image, not a wrapper, because `handleError` uses `img.nextElementSibling` to show the text fallback); the fallback `<span>` is unchanged. This applies wherever `TenantLogo` is used (`LoginPage`, `BrandingPreview`, `VerifyCertificatePage`). Light theme: no change.
- [ ] AC-10: Charts follow the theme. A hook `frontend/src/hooks/useThemeColors.ts` returns an object of colours read with `getComputedStyle(document.documentElement)` inside a `useLayoutEffect` keyed on `resolved` from `useTheme()` and on the tenant primary (from `useTenantConfig`), stored in state, so consumers re-render with the new theme (the class is already applied, AC-2). Mapping: axis lines, grid lines, tracks and the unassigned part of bars (`#e5e7eb` today) use `--color-border-default`; primary bars, lines and arcs use the tenant primary when set, else `--color-primary`; tick and axis text uses `--color-text-secondary`; muted labels use `--color-text-muted`. `PassRateChart` and `CompletionBarChart` use it; their `primaryColor` prop still wins when given and the `#6366f1` fallback is removed; `ScoreDial` takes its track colour from the hook instead of `stroke="#e5e7eb"`. Tests stub `getComputedStyle` (jsdom does not load `index.css`) and assert the colours change when the theme switches.
- [ ] AC-11: Contrast in both themes. `@axe-core/playwright` is a devDependency (added by FR-BB320 Part A together with the helper `frontend/e2e/fixtures/axe.ts` that runs `new AxeBuilder({ page }).withRules(['color-contrast'])`; if that part is not merged yet, add both here). - [ ] AC-12: Other tests. vitest (with `window.matchMedia` stubbed): `ThemeProvider` (default system; stored light and dark; invalid stored value ignored; storage throwing; OS change while `system`; no change when explicit; listener removed on unmount; class applied before state update), `ThemeToggle` (roles, arrow keys, accessible name, `setPreference` called), `TenantProvider` foreground for a light and a dark tenant colour, removal of overrides when config is absent, `readableForeground` (white, dark, 3-digit, invalid), `TenantLogo` classes on the img and the fallback span intact. ## Technical Specification
- No migration and no backend change.
- Files: `frontend/public/theme-init.js`, `frontend/index.html`, `frontend/src/components/ThemeProvider.tsx`, `ThemeToggle.tsx`, `components/auth/AuthShell.tsx`, `lib/contrast.ts`, `hooks/useThemeColors.ts`, `App.tsx`, `components/admin/TopBar.tsx`, `layouts/PortalLayout.tsx`, `pages/VerifyCertificatePage.tsx`, the four auth pages of AC-6, the seven files of AC-13, `components/TenantProvider.tsx`, `TenantLogo.tsx`, `PassRateChart`, `CompletionBarChart`, `ScoreDial`, `deploy/nginx.conf` only, locale files, e2e specs.
- The `.dark` token block in `index.css` exists; its contrast values are corrected by FR-BB320 AC-1, which is why Part A of that requirement merges first.
- The design system text says `data-theme="dark"`; the code mechanism is `class="dark"` and stays (`docs/design-system/foundations.md`).
- `deploy/nginx.conf` is a protected path (architect decision before merge); the host vhosts are not touched.

## Out of Scope
- Saving the theme on the user account or syncing across devices.
- A per-tenant default theme, scheduling by time of day, a high-contrast mode, print styles.
- Server-rendered documents (certificate PDFs, dashboard PDF) stay light.
- Redesigning dark token values beyond FR-BB320 AC-1.

## Test Strategy
See AC-3, AC-10, AC-11, AC-12 and AC-13. UAT: switch themes on each layout, reload, change the OS theme while on `system`, check logo, charts, badges and tenant colours, and take an exam in dark theme.
