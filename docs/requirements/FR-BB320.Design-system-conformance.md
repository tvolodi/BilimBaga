## Description
The owner's design system (58 components with previews, tokens synced from `main@2a4ad2d`) is now in the repo as the project rule for UI work (`docs/design-system/`). Comparing it with the code shows three kinds of gaps: (1) token values that fail the contrast target of FR-BB63, (2) component differences between the system and the app, and (3) nothing enforces the rules: 17 raw hex colour literals on 16 lines in 10 `.tsx` files, about 100 raw `<button>`, `<input>`, `<select>`, `<textarea>`, `rgb(` or `hsl(` uses outside `components/ui/`, no component gallery and no visual regression tests. This requirement closes them in four parts, implemented as separate dev issues: **A before D; B can merge at any time; C is independent; D needs A, C and a fixed screenshot environment.**

**Dark theme status (verified 2026-10-10):** `index.css` defines dark tokens under a `.dark` class on `<html>`, but nothing in the app sets that class and there is no theme switch, so users cannot reach dark mode today. Dark-theme values are fixed here so they are correct when a switch is added, but real-page dark checks are out of scope. (The design system text says `data-theme="dark"`; the code uses `class="dark"`, which stays; `foundations.md` is corrected.)

## Acceptance Criteria

### Part A — Tokens and component differences
- [ ] AC-1: Contrast. In `frontend/src/index.css`, `docs/design-system/tokens.json` (including its usage notes that say "source value kept") and `docs/design-system/foundations.md`, set `--color-text-muted` (captions, placeholders, timestamps) to `#5f6b7d` in the light theme (line 34 today `#8A94A6`: 3.06:1 on white, 2.83:1 on the page background) giving 4.81 to 5.4:1 on white, page and subtle backgrounds, and to `#8fa0b4` in the dark theme (line 142 today `#5A6A7E`: 2.90:1 on surface) giving 5.16 to 6.78:1 on page, surface, raised and subtle backgrounds. Set the dark-theme `--color-destructive-foreground` (line 168, text on the destructive fill `#E06050`) to `#0f1623` (5.14:1; white was 3.52:1). `color-gold` (2.29:1 on white) is never used for text or as the only mark; gold badge text uses `#7a5e1a` on `color-gold-light` (4.79:1). `--color-muted-foreground` (`#4A5568` light, `#9AAABB` dark) already passes and stays. Values were computed with the WCAG relative-luminance formula; a developer may adjust a value only if every ground in both themes stays at or above 4.5:1, records the numbers in the PR, and updates the three files together.
- [ ] AC-2: Sidebar. `components/admin/Sidebar.tsx` replaces `bg-gray-900`, `bg-gray-700` and `text-gray-*` with the navy tokens (`color-bg-navy` `#1b3a6b`, text `color-text-on-navy`, hover and active fills derived from navy as in the design system's Sidebar README). The `@theme` block already exposes `--color-navy`, `--color-bg-navy` and `--color-text-on-navy`; the utility class names follow the keys: `bg-navy` or `bg-bg-navy`, `text-text-on-navy`. Use these existing names; add an alias only if a token is missing.
- [ ] AC-3: Badge. `components/ui/badge.tsx` success, warning, danger and info variants use the semantic pairs (`color-success` on `color-bg-success`, `color-warning` on `color-bg-warning`, `color-danger` on `color-bg-danger`, `color-info` on `color-bg-info`) instead of Tailwind `green-100`, `yellow-100` and similar. The utilities follow the `--color-*` keys (`text-success`, `bg-bg-success`, `text-warning`, `bg-bg-warning`, `text-danger`, `bg-bg-danger`, `text-info`, `bg-bg-info`); add any that are missing to the `@theme` block.
- [ ] AC-4: Dialog and Sheet accessibility. `components/ui/dialog.tsx` already has `role="dialog"`, `aria-modal`, Escape, a focus trap and focus return to the opener; do NOT rewrite it. Add: `aria-labelledby` pointing at the id of `DialogTitle` and `aria-describedby` pointing at `DialogDescription` when present (ids generated with `useId` in the Dialog root and shared through context), and verify that initial focus moves into the dialog on open (add it if it does not: first focusable element, or the content container with `tabIndex={-1}`). `components/ui/sheet.tsx` has none of this today; give it all of it: `role="dialog"`, `aria-modal="true"`, the same labelledby and describedby wiring, focus moved in on open, a focus trap, Escape closes, focus returns to the opener, overlay click closes.
- [ ] AC-5: Tests. vitest for AC-3 (each variant renders the expected token classes) and AC-4 (aria attributes, initial focus, Tab wrap, Escape, focus return) for Dialog and Sheet; `dialog.test.tsx` is extended and `sheet.test.tsx` added. In `frontend/e2e/accessibility.spec.ts` the existing pages stay at zero `color-contrast` violations in the light theme after AC-1. A dark-theme axe run is added for the login page only, setting the theme the way the app would (`document.documentElement.classList.add('dark')` before `axe.analyze`), with zero `color-contrast` violations.

### Part B — Enforcement by lint
- [ ] AC-6: `npm run check:design` (a script `frontend/scripts/check-design.ts` in the style of `check-i18n.ts`, added to the `test` script after `check:i18n`) fails when any `.ts` or `.tsx` file under `frontend/src` contains a hex colour literal, an `rgb(` or `hsl(` colour, a Tailwind arbitrary colour class (`bg-[#…]`, `text-[#…]`, `border-[#…]`), or a raw `<button`, `<input`, `<select` or `<textarea` element outside `frontend/src/components/ui/`. Excluded: `*.test.ts(x)`, `index.css`, and `frontend/src/pages/DesignGallery/`. A line may carry `// design-ok: <reason>` and a file may carry a first-line `/* design-ok-file: <reason> */`; the reason is mandatory and printed in the report. `BrandingPreview.tsx` and `BrandingSettingsPage.tsx` get a `design-ok-file: tenant colour editor` marker. Known literals to handle in AC-7's hex pass: `ColorPickerField.tsx:80` (`'#000000'`, mark with `design-ok`), and the chart fallbacks `#e5e7eb` and `#6366f1` in `PassRateChart`, `CompletionBarChart` and `ScoreDial` (replace with tokens or mark).
- [ ] AC-7: Ratchet for existing violations. The raw-element and `rgb(`/`hsl(` hits that exist today (about 100) are recorded in `frontend/scripts/design-baseline.json` as `{file: count}`; the check passes while a file's count does not exceed its baseline and fails on any new file or higher count. Lowering a count requires lowering the baseline in the same PR (the script rejects a baseline larger than the real count with "baseline can be lowered"). Hex literals are not baselined: the 17 existing literals (list: run the script once) are each replaced by a token class or marked `// design-ok: <reason>`.
- [ ] AC-8: Tests: the script exposes a pure function (for example `checkDesign(files, baseline)`) and its vitest unit test lives at `frontend/src/scripts/check-design.test.ts` (vitest only includes `src/**/*.test.*`, so a test next to the script would be skipped), using in-memory fixture files (violation, `design-ok` line, `design-ok-file`, baseline equal, baseline exceeded, baseline can be lowered, clean). `npm test` exits 0 on the repository after AC-7 and prints the number of `design-ok` exceptions and the baseline total.

### Part C — Component gallery and interaction audit (no baselines)
- [ ] AC-9: A development-only route `/__design` (registered only when `import.meta.env.DEV` or `VITE_ENABLE_DESIGN_GALLERY === 'true'`; absent from the production build, covered by a test that checks the production route table) renders every component in `frontend/src/components/ui/` from a data-driven list in `frontend/src/pages/DesignGallery/states.ts`. Minimum states per component: Button and Badge, every variant and size; Input, Select, Textarea (if present), Label: default, filled, disabled, `aria-invalid`; Card: with header, content, footer; Table: with rows and an empty row; Skeleton: default; Dialog, Sheet, Popover: an open instance inside the gallery; date-time-picker: default and disabled. Each section can be shown in a `.dark` wrapper (class on a container) and in `kk`, `ru`, `en` through a locale switch. The directory is excluded from `check:i18n` and `check:design`.
- [ ] AC-10: Exam-mode audit in Playwright (`frontend/e2e/design-audit.spec.ts`): on the exam-taking page every interactive element has a bounding box of at least 44 by 44 px, and after pressing Tab each such element shows a visible focus indicator (computed `outline-width` greater than 0 or a `box-shadow` that differs from the unfocused state). Uses the existing `createTestExam` and `startEmployeeSession` helpers in `frontend/e2e/fixtures/seed.ts`.

### Part D — Visual regression baselines (needs A, C and an environment)
- [ ] AC-11: A fixed screenshot environment exists and is documented: new `Makefile` targets `visual-test` and `visual-update` (added to `.PHONY`) run Playwright inside `mcr.microsoft.com/playwright:v<version>-jammy` where `<version>` is the exact `@playwright/test` version resolved in `frontend/package-lock.json` (`package.json` has the range `^1.60.0`). The container builds the frontend (`npm run build`) and uses the existing `webServer` setting (`npm run preview`); the backend and database from the dev stack must be reachable from the container (for example `host.docker.internal`), with `E2E_BASE_URL` and the API URL passed in as environment variables, because the page baselines of AC-13 use `seed.ts`. Baselines are therefore identical on every machine. Optionally a CI job runs the same container. Baselines are never generated on Windows or macOS directly. (`playwright.config.ts` today has one chromium project against `npm run preview` and no screenshot settings; add `expect.toHaveScreenshot` defaults `maxDiffPixelRatio: 0.01`, `animations: 'disabled'`.)
- [ ] AC-12: `frontend/e2e/design-gallery.spec.ts` loads the gallery once per width and locale combination and takes ONE full-page `toHaveScreenshot` of the gallery in the light theme at widths 375, 768 and 1280 in `kk`, `ru` and `en` (9 baselines), plus one with every section in the `.dark` wrapper at 1280 in `en` (10 baselines in total, not one per component). Baselines are committed under `frontend/e2e/design-gallery.spec.ts-snapshots/`. A PR that changes a baseline says why in its description.
- [ ] AC-13: Page baselines for login, admin dashboard, users list, question bank list, employee portal, exam taking and result screen, at 1280 and 375 in `en` and `kk`, light theme only. Data comes from `frontend/e2e/fixtures/seed.ts` (`createTestExam`, `startEmployeeSession`, plus a submitted session for the result screen); dynamic nodes (dates, ids, durations, counts derived from the clock) carry `data-visual-mask` and are passed to `toHaveScreenshot` as `mask`.

## Technical Specification
- No migration and no backend change.
- Tenant branding (`TenantProvider`) overrides `color-primary` and `color-accent` at runtime; those tenant colours are not covered by AC-1. A follow-up could validate the tenant primary against white text (4.5:1) in the branding settings form.
- The design system artifact's bundle is a specification and preview source only; it does not replace shadcn/ui or Tailwind in the app.
- The old design document's icon section was corrected to `lucide-react` by the BA in the same change that introduced this requirement; no code change.
- The theme mechanism is `class="dark"` on `<html>` (see Description). A theme switch UI is not part of this requirement.

## Out of Scope
- Rebuilding the frontend on the artifact's component bundle.
- Storybook or any third-party visual-testing service.
- Contrast validation of tenant-chosen colours.
- A dark-mode switch and dark checks of real pages. Dark mode is defined in the tokens but unreachable; whether to ship it is the owner's decision.
- Replacing the roughly 100 raw elements outside `components/ui/`; they are baselined by AC-7 and removed over time.
- New components not in the design system.

## Test Strategy
AC-5, AC-8, AC-9 (route table test), AC-10, AC-12 and AC-13 are the tests. UAT: open the app in the light theme with `kk`, `ru`, `en` and compare against the design system previews.
