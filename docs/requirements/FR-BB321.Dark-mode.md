## Description
`frontend/src/index.css` already defines the dark tokens under a `.dark` class on `<html>` (it uses no `color-scheme` property yet), but nothing in the app sets that class and there is no switch, so users cannot reach dark mode. This requirement adds it: a three-way preference (light, dark, system), a switch on every layout, no flash of the wrong theme on load, theme-aware charts, logo and tenant colours, and contrast checks of the key pages in both themes. The design system (`docs/design-system/foundations.md`) already specifies the dark values.

## Decisions (BA, 2026-10-10)
- **D-1 Preference values:** `light`, `dark`, `system`. Default `system` (follows `prefers-color-scheme` and later OS changes while the page is open).
- **D-2 Stored on the device, not on the account:** `localStorage` key `bb-theme`. No migration, no API change. Per-account sync is a possible follow-up (the locale is account-bound, FR-BB116; the theme deliberately is not).
- **D-3 Mechanism:** the existing `class="dark"` on `<html>` plus the CSS `color-scheme` property (`light` or `dark`) set on `<html>` so native controls and scrollbars follow.
- **D-4 No flash:** a blocking classic script `frontend/public/theme-init.js`, referenced from `<head>` of `frontend/index.html` before the app, sets the class and `color-scheme` before first paint. It is a same-origin file, not an inline script, so it keeps working if the CSP drops `'unsafe-inline'` (FR-BB64; today `script-src 'self' 'unsafe-inline'`).
- **D-5 Exam mode:** no switch in the exam bar (exam mode has no navigation except the exam bar), but the stored theme applies on the exam screen.
- **D-6 Tenant colours (DEC-002 section 4).** The tenant primary applies to the light theme as stored (the API guarantees at least 4.5:1 against white, 422 otherwise). In the dark theme it is NOT applied as stored: a colour that passes on white fails on the dark grounds. The dark theme uses a colour DERIVED from the tenant primary by lightening it (same hue and saturation, lightness increased) until it meets the dark floor, or the design-system dark pair when no such colour exists (AC-8). The server stores one colour per tenant; the derivation is client-side and deterministic. The contrast floor everywhere is 4.5:1 (normal text, WCAG AA), measured against every dark ground (`#0F1623` page, `#1A2133` surface, `#222D42` raised, `#1E2A3D` subtle) and between the fill and its foreground.
- **D-7 The result screen** renders inside `PortalLayout` and so shows the toggle; D-5 excludes only the exam bar and `ExamLayout`.

## Acceptance Criteria
- [ ] AC-1: `frontend/src/components/ThemeProvider.tsx` exposes `{ preference, resolved, setPreference }` through a context and a `useTheme()` hook. `preference` is `light | dark | system`; `resolved` is `light | dark`. On mount it reads `localStorage['bb-theme']`; a missing, unparsable or unknown value is treated as `system`; every `localStorage` access is in try/catch (private mode, blocked storage) and the provider works without storage. The context has a default value (`preference: 'system'`, `resolved: 'light'`, `setPreference` a no-op) so `useTheme()` never throws outside the provider; existing tests that render `TenantLogo`, `LoginPage` or `BrandingPreview` without a provider keep passing. `setPreference` stores the value (removes the key for `system`) and applies it.
- [ ] AC-2: Applying a theme adds or removes `class="dark"` on `document.documentElement` and sets `document.documentElement.style.colorScheme` to `light` or `dark`; this happens synchronously inside `setPreference` and the `matchMedia` handler BEFORE the React state is updated, so any component that reads CSS variables after a state change sees the new theme. With `system`, the provider subscribes to `window.matchMedia('(prefers-color-scheme: dark)')` change events and re-applies; the subscription is removed on unmount.
- [ ] AC-3: `frontend/public/theme-init.js` (classic script, not a module, no requests, wrapped in try/catch, at most 30 lines) applies the same rules as AC-1 and AC-2 for the first paint. `frontend/index.html` references it in `<head>` as `<script src="/theme-init.js"></script>` (no `type="module"`; Vite leaves such a tag alone, so the file is neither bundled nor hashed, and serves `public/` at `/` in dev and copies it to `dist/` in the build). A vitest test reads the file text and runs it with `new Function(text)()` in jsdom for: stored `dark`, stored `light`, stored invalid value, storage throwing, OS dark without a stored value, OS light without a stored value (`window.matchMedia` stubbed per test, because jsdom does not implement it).
- [ ] AC-4: nginx serves the script without long caching. Only `deploy/nginx.conf` serves the frontend (it is copied into the image by `deploy/Dockerfile`); add there `location = /theme-init.js { try_files $uri =404; add_header Cache-Control "no-cache" always; ... }` and repeat inside it the five `add_header ... always` lines of the server block (`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy "same-origin"`, `Strict-Transport-Security $hsts`), because `add_header` is not inherited into a location that declares its own. Do NOT change `deploy/nginx/bilimbaga.conf`, `bilimbaga-qa.conf` or `bilimbaga-test.conf`: they are host reverse proxies that pass headers through, and `bilimbaga-test.conf` is the customer demo that swarm roles never touch (CLAUDE.md owner rule).
- [ ] AC-5: `frontend/src/components/ThemeToggle.tsx` is a three-button radio group (`role="radiogroup"` with an accessible name; each button `role="radio"` with `aria-checked`; roving `tabindex` and arrow keys; built on `components/ui/button`) for Light, System, Dark, with lucide icons `Sun`, `Monitor`, `Moon`. No dropdown (the repo has no dropdown-menu primitive). Below 640 px each button is at least 44 px (`min-h-11 min-w-11`).
- [ ] AC-6: Placement. `ThemeProvider` sits in `frontend/src/App.tsx` directly inside `QueryClientProvider`, wrapping `TenantProvider` and `BrowserRouter`, so every route including `/verify/...` follows the theme. The toggle is rendered in: `components/admin/TopBar.tsx` between `LocaleSwitcher` and the profile link; the inline `<nav aria-label="Portal navigation">` of `frontend/src/layouts/PortalLayout.tsx` (this also covers the result screen, D-7); `pages/VerifyCertificatePage.tsx` in its existing top row next to its `LocaleSwitcher` (a fixed corner toggle would overlap it at 375 px); and, for the four auth pages that have no shared layout, a new `components/auth/AuthShell.tsx` that renders a fixed top-end corner toggle (`fixed top-4 end-4`) around its children, used by `pages/auth/LoginPage.tsx`, `ChangePasswordPage.tsx`, `ForgotPasswordPage.tsx` and `ResetPasswordPage.tsx` (their own markup stays inside; check 375 px for overlap with their language selector). `/change-password` is a standalone route under `RequireAuth` with no other layout, so the shell is not doubled there.. - [ ] AC-7: i18n keys in `kk`, `ru`, `en`: `theme.label`, `theme.light`, `theme.system`, `theme.dark`. No hardcoded strings; `npm run check:i18n` stays green.
- [ ] AC-8: Tenant colour mapping. `frontend/src/lib/contrast.ts` (first line `/* design-ok-file: colour maths needs literals */`) exports: the constant `DARK_GROUNDS = ['#0f1623', '#1a2133', '#222d42', '#1e2a3d']`; `parseHex(hex)` returning `[r, g, b]` or `null` for anything that is not `#rgb` or `#rrggbb` (case-insensitive); `contrastRatio(a, b)` (WCAG relative luminance) returning `1` when either argument does not parse; `readableForeground(hex)` returning `#ffffff` or `#0f1623`, whichever has the higher contrast against `hex`, `#ffffff` on a tie or an invalid input; and `deriveDarkColour(hex)`. `deriveDarkColour` is exact: return `null` if `hex` does not parse; a colour is acceptable when `min(contrastRatio(c, g) for g in DARK_GROUNDS) >= 4.5` AND `contrastRatio(readableForeground(c), c) >= 4.5`; if `hex` is acceptable return it (lowercase); otherwise convert to HSL with exact (unrounded) hue and saturation, let `L0 = round(lightness * 100)`, and for `l = L0 + 1 ... 90` build the colour from the original hue and saturation with lightness `l / 100`, convert to hex with each channel `Math.round(value * 255)` and lowercase output, and return the first acceptable colour. For every valid hex the loop succeeds at or before 90 (checked: all hues reach 4.5:1 on all four grounds by that lightness); a `null` after the loop is a defensive branch that the provider treats like an invalid input. `TenantProvider` applies in a `useLayoutEffect` and then increments a `version` value exposed in its context so consumers re-read computed styles (AC-10): The primary and its foreground are written as STYLESHEET RULES in a `<style>` element owned by the provider (`:root:not(.dark) { --color-primary: ...; --color-primary-foreground: ...; }` for the light theme and `:root.dark { ... }` for the dark theme), so the class on `<html>` selects the rule; an inline style is NOT used for the primary because an inline value would outrank the `.dark` token block (architect ruling on PR 462, DEC-002 section 4). `--color-accent` and `--color-accent-foreground` stay inline styles on `<html>`, set for the current theme. (1) LIGHT theme: `--color-primary` is the tenant primary and `--color-primary-foreground` is `readableForeground(primary)`, but only when `contrastRatio(primary, '#ffffff') >= 4.5`; a primary below 4.5 (a legacy value chosen before the DEC-002 rule) is ignored in every theme, the design-system value stays, and the branding settings page shows the ratio and the API rule's message so an admin can fix it. (2) DARK theme: if the tenant primary equals the design default (`#2e6db4`, case-insensitive) or was ignored, no override is set (and any override set earlier, for example before a light-to-dark switch, is removed) and the design-system dark pair stays (`#5AA0E0` with `#0F1623`, 6.50:1); otherwise `--color-primary` is `deriveDarkColour(primary)` with `--color-primary-foreground` from `readableForeground`, and a `null` result leaves the dark pair. (3) Accent: `--color-accent` is set (inline on `<html>`, for the current theme) to the stored accent in the light theme, and in the dark theme to nothing when it equals the design default `#c8a84b` (a previous override is removed), otherwise to `deriveDarkColour(accent)` or, on `null`, nothing. In BOTH themes `--color-accent-foreground` is set to `readableForeground(<the accent applied in that theme>)`, and is removed together with the accent override so the token value returns. (4) When the tenant config is absent or has no primary, all overrides are removed; when only the accent is absent only `--color-accent` is removed. Overrides are recomputed whenever `resolved` or the tenant config changes. Links and focus rings in dark theme keep `--color-text-link` and `--color-ring` from the dark tokens. Per DEC-002 section 4 rule 4, text on a primary tint (`bg-primary/10`) uses `text-foreground`, not `text-primary`, in both themes; the derived colour is only checked against the grounds, not against tints. The `TenantProvider` context has a default value (`version: 0`) so `useThemeColors` works outside the provider. `BrandingPreview` renders with the same resolved colours as the current theme, so an admin sees the dark result too, and `BrandingSettingsPage` shows the light-theme ratio (DEC-002 rule 2) next to the picker.
- [ ] AC-9: Logo. `TenantLogo` calls `useTheme()`. When `resolved === 'dark'` the `<img>` itself (default mark or tenant upload) gets `bg-white rounded-md p-1` (classes directly on the image, not a wrapper, because `handleError` uses `img.nextElementSibling` to show the text fallback); the fallback `<span>` is unchanged. This applies wherever `TenantLogo` is used (`LoginPage`, `BrandingPreview`, `VerifyCertificatePage`). Light theme: no change.
- [ ] AC-10: Charts follow the theme. The hook reads the RESOLVED `--color-primary` from computed style (it carries the derived dark colour); it does not read the raw tenant primary from `useTenantConfig`. Mapping: axis lines, grid lines, tracks and the unassigned part of bars (`#e5e7eb` today) use `--color-border-default`; primary bars, lines and arcs use the resolved `--color-primary`; tick and axis text uses `--color-text-secondary`; muted labels use `--color-text-muted`. `PassRateChart`, `CompletionBarChart` and `ScoreDistributionChart` use it; their `primaryColor` prop still wins when given and the `#6366f1` fallback is removed; `ScoreDial` takes its track colour from the hook instead of `stroke="#e5e7eb"`. Tests stub `getComputedStyle` (jsdom does not load `index.css`) and assert the colours change when the theme switches and when the tenant colour changes.

## Technical Specification
- No migration and no backend change.
- Files: `frontend/public/theme-init.js`, `frontend/index.html`, `frontend/src/components/ThemeProvider.tsx`, `ThemeToggle.tsx`, `components/auth/AuthShell.tsx`, `lib/contrast.ts`, `hooks/useThemeColors.ts`, `App.tsx`, `components/admin/TopBar.tsx`, `layouts/PortalLayout.tsx`, `pages/VerifyCertificatePage.tsx`, the four auth pages of AC-6, `BrandingSettingsPage.tsx` and `BrandingPreview.tsx` (they still fall back to the old seed defaults `#0ea5e9` and `#f59e0b` at lines 78 and 85; DEC-002 rule 1, issues #443 and #444, replace those defaults and this requirement consumes the result), the seven files of AC-13, `components/TenantProvider.tsx`, `TenantLogo.tsx`, `lib/tenantColours.ts`, `PassRateChart`, `CompletionBarChart`, `ScoreDistributionChart`, `ScoreDial`, the callers `AdminDashboardPage`, `ExamAnalyticsPage` and `ResultPage`, `deploy/nginx.conf` only, locale files, e2e specs.
- The `.dark` token block in `index.css` exists; its contrast values are corrected by FR-BB320 AC-1, which is why Part A of that requirement merges first.
- The design system text says `data-theme="dark"`; the code mechanism is `class="dark"` and stays (`docs/design-system/foundations.md`).
- `deploy/nginx.conf` is a protected path (architect decision before merge); the host vhosts are not touched.

## Out of Scope
- Saving the theme on the user account or syncing across devices.
- A per-tenant default theme, scheduling by time of day, a high-contrast mode, print styles.
- Server-rendered documents (certificate PDFs, dashboard PDF) stay light.
- Redesigning dark token values beyond FR-BB320 AC-1.
