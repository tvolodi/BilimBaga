# DEC-003: Who May Set an Exam's AI Grading Mode to `auto`

| Field | Value |
|-------|-------|
| Type | Decision record (not an FR-BB requirement) |
| Status | Proposed: options and a recommendation; the choice is the owner's |
| Date | 2026-10-11 |
| Decided by | Pending (owner). Input: architect review of PR 558 (#546), issue #560 |
| Owner | Business Analyst keeps the doc; Dev implements after the decision |

## 1. Context

FR-BB73 revision 2 gives every exam an `ai_grading_mode` of `off`, `suggest` or `auto` (default `suggest`). In `auto` an AI score that cannot decide pass or fail, and that carries no flag, becomes the grade, with the result mail and the certificate following without a person looking at it. Today (main, PR 558) the mode is a field of the exam create and update requests, so anyone who passes `exams:write` can set it: `examiner` and `super_admin` (migration 005), and any custom role the owner grants `exams:write` through role management (FR-BB117). `department_admin` holds `exams:read` and `exams:assign` only. The risk is not the AI itself but the fact that the switch that removes human review sits with a routine editing permission.

## 2. Options

| | Option | Who can set `auto` | Cost | Effect on today's data |
|--|--------|--------------------|------|------------------------|
| A | Keep as is | every `exams:write` holder | none | none |
| B | New permission `exams:ai_auto` | `super_admin` (through the seed row of the new migration, as migration 034 did for `roles:*`) and any custom role the owner grants it; not `examiner` | one migration seeding the permission and its super_admin row, a permission check in the exam create and update handlers, one i18n string, role-management UI lists it automatically (FR-BB117 `GET /roles/permissions` reads the permission table; FR-BB117 AC-6 blocks only `roles:*` and `tenant:manage` for custom roles, so `exams:ai_auto` is grantable) | none: every exam is `suggest` by default |
| C | Tenant switch | any `exams:write` holder, but only while a tenant setting `ai_grading_auto_allowed` (default false, set by `super_admin`) is true | a tenant config key (FR-BB13) plus a check, UI on the branding or tenant settings page | none |
| D | Deployment setting only | nobody in the UI; the owner sets it per host in the environment | a config variable and a check | none; `auto` cannot be used without a deploy |

Rules common to B, C and D: moving an exam **away** from `auto` (to `suggest` or `off`) never needs the extra right; editing other fields of an exam already in `auto` keeps the mode and needs only `exams:write`; a request that would move an exam **into** `auto` without the right answers 403 `ERR_FORBIDDEN` (the code the exam handlers use; the `rbac` middleware answers `FORBIDDEN` for route-level checks), on create and on update; every change of the mode is written to the audit row of `exam.update` with the old and the new value (`ai_grading_mode_from`, `ai_grading_mode_to`). The audit row carries only `title` today and `UpdateExam` returns only the new row, so this needs a pre-read of the exam in the service (an empty `ai_grading_mode` in the request keeps the old value); the cost is the same for B, C and D.

Note: `UpdateExam` answers `EXAM_NOT_DRAFT` for a non-draft exam today. The rule "editing other fields of an exam already in `auto`" therefore applies to draft exams only until a separate dev issue lets the mode change in every status (FR-BB73 AC-9, AC-22); that fix is independent of this decision.

## 3. Recommendation

**B.** It is the smallest change that fits the RBAC model the product already has (permissions are rows, roles are assignable, FR-BB117 already shows and edits them), it can be given to one trusted custom role without a deploy, it leaves a clear audit trail, and it costs one migration. It is T4 for the dev change (new migration, `rbac` seed), so the architect reviews the PR. C would put a global flag between the owner and a per-exam choice and gives no per-person control. D is the safest and the least convenient; it is the right choice only if the owner wants `auto` unavailable until a deliberate deploy. A leaves the review-removing switch with the routine editor and is not recommended.

## 4. What the owner decides

1. A, B, C or D.
2. For B: whether the permission is held by `super_admin` only (recommended) or also seeded to `examiner`.
3. Whether `auto` stays unused until FR-BB73 has run in `suggest` for a period (the default already makes this the starting state).

## 5. After the decision

BA amends FR-BB73 AC-22 (exam setting) and adds the next free AC (AC-25 at the time of writing) for the permission rule, and files the dev issue. Until then the dev may not change the exam permission model. The issue #560 stays `status:blocked` (owner decision).
