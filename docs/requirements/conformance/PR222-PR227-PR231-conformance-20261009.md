# Conformance Review: PR #222, PR #227, PR #231 (FR-BB117 D-1, security-critical)

- Date: 2026-10-09
- Reviewer: Business Analyst (static code review; no live stack, no UAT executed, tests not re-run)
- Base: origin/main at 81ec924 (worktree `ba`, branch swarm/ba-conformance-d1)
- Scope: PR #222 (02301ae, ISS-217: D-1 target-role rule on reset/update/deactivate/unlock plus assignment rule), PR #227 (8df024d, ISS-226: frontend assignable roles, localized 403), PR #231 (81ec924, ISS-229: per-caller `assignable` flag on `GET /users/roles`).
- Compared against: FR-BB117 "Decisions 2026-10-09" D-1 (amended), FR-BB18 AC-4 / AC-6 / AC-10, FR-BB115 AC-5 (unlock).
- Severity: p1 = privilege escalation or data exposure; p2 = behaviour/spec defect or latent weakness; p3 = minor/documentation.

## Verdict

**p1 gaps: none. No bypass of D-1 found.** Every state-changing path that takes a target user runs the authorization decision before any password generation, hashing, repository write, token revocation or e-mail. The decision is one fail-closed function (`canReachRole`) shared by target checks, assignment checks and the `assignable` flag. Two p2 items (equal-permission custom-role peers; stale token claims) and several p3 items are listed in section 3.

## 3. Gap list

| ID | Sev | Gap | Evidence | Suggested action |
|----|-----|-----|----------|------------------|
| G1 | p2 | Authorization uses role, department and status claims from the JWT. The per-request account lookup checks only password epoch and force-change flag, so a demoted, moved or deactivated caller keeps old rank, scope and API access for up to `JWT_ACCESS_TTL_MINUTES` (15). Pre-existing, outside the three PRs, but it weakens D-1 after a role change | `auth/middleware.go:92-117`, `backend/.env.example:21` | Decide: re-read role, department, status in the account-state lookup (fail closed), or accept and document the 15 minute window |
| G2 | p2 (spec decision) | Permission subset is inclusive: a custom role with exactly the caller's permissions is reachable and assignable. A department_admin can assign a custom clone of department_admin and so mint a peer, contrary to the strictly-lower intent; a custom caller can assign its own role to others and manage peers. Not p1: a super_admin must first create such a role, and sensitive permissions stay excluded | `service.go:555-572`; "custom vs same custom role" allowed in `privilege_escalation_test.go` `TestD1_AllowedTargets` | Product decision: require a proper subset (reject roles whose set equals or exceeds the caller's) |
| G3 | p3 | D-1 states "no self role change" without exemption; code exempts super_admin (`!isOrgWide`), so a super_admin can demote itself; any caller may deactivate itself (self exemption). Last-super_admin lockout not guarded | `service.go:218`, `:515` | Add to spec (allowed for super_admin) or forbid; consider last-super_admin guard |
| G4 | p3 | Malformed (non-UUID) path id, `role_id` or `department_id` gives 500 `INTERNAL_ERROR` (Postgres cast error wrapped), not 404 or 422; a scoped caller with a malformed `role_id` gets 500 from `checkRoleAssignment`. Not verified live | `repository.go:95-110`, `service.go:474-480`, `handler.go:189-195` | Validate UUIDs in the handlers as `ListUsers` does (`api.UUIDQuery`) |
| G5 | p3 | Read-check-write without transaction or conditional update: a concurrent role change of the target between `GetByID` and the write is not detected (needs two privileged actors) | `service.go:205-240`, `repository.go:157-170` | Optional: `UPDATE ... WHERE id=$ AND role_id=$expected` |
| G6 | p3 | Routed users page does not surface 403 for reset-password (silent) or unlock (generic message); actions shown for non-actionable targets | `frontend/src/pages/admin/users/UsersListPage.tsx:58-59,89-97` | Reuse `userErrorKey`; optionally disable actions with the same rank rule |
| G7 | p3 (latent) | Import resolves department and role by name twice (validate, then commit) with `SELECT id FROM departments WHERE name=$1 LIMIT 1` and no ordering, while department names are unique only per parent. With two same-named departments in different branches the validated and the committed department could differ, which could defeat the scope check in theory | `service.go:390,421`, `repository.go:225-232`, `migrations/006_departments.up.sql:9` | Resolve once per row and reuse the ids; treat an ambiguous name as a row error |
| G8 | p3 | Unknown id answers 404 while an existing out-of-scope id answers 403, so a `users:manage` caller can probe whether a UUID exists | `service.go:205-211` | Optional: 404 for out-of-scope targets |

## 4. Test coverage

Existing (`backend/internal/users/`):

- `privilege_escalation_test.go` `TestD1_ForbiddenTargets`: 18 caller/target pairs, each across 4 operations (reset, update, deactivate, unlock), asserting 403, empty temporary password and no writes. Pairs: dept_admin vs super_admin, peer dept_admin, custom role with permissions it lacks, legacy empty role; examiner vs dept_admin, peer examiner, super_admin; employee vs employee, examiner; unknown and empty caller role vs employee; `ex_custom` vs dept_admin; `narrow_custom` vs examiner; `user_helper` vs super_admin, dept_admin, examiner, employee, legacy.
- `TestD1_AllowedTargets`: 11 allowed pairs x 4 operations (dept_admin vs employee, examiner, narrower custom; examiner vs employee; custom subset pairs; super_admin vs all).
- `TestD1_OtherDepartmentStillForbiddenEvenWhenSubset`, `TestD1_SelfServiceStillWorks`, `TestD1_SelfServiceUnchanged` (stale token role), `TestD1_FailClosedWithoutPermissionLookup`, `TestD1_RankTable`.
- Assignment: `TestD1_UpdateCannotAssignSuperAdminOrMorePowerfulRole` (dept_admin only), `TestD1_AssignmentHierarchy` (15 cases, create path only), `TestD1_CustomRoleWithSensitivePermsNotAssignable` (create only), `scoping_test.go` (custom scope, import `super_admin` row in preview, own-role-change, custom caller cannot assign more powerful).
- Handler: reset 403 without password, reset allowed for employee, deactivate and unlock 403, peer dept_admin (`privilege_escalation_test.go:207-266`).
- Flag (PR #231): `roles_assignable_test.go` for super_admin, dept_admin, custom, examiner, employee, unknown caller, parity with `checkRoleAssignment`, handler shape.
- Frontend: `assignableRoles.test.ts`, `UserRoleAssignment.test.tsx`, `useAssignableRoles.test.tsx`.

Missing (none blocks merge):

1. Rank pairs: a custom role equal to department_admin's permissions (G2) as target and as assigned role; equal-set custom vs custom; examiner and employee callers vs custom roles; dept_admin vs examiner on `update` with a role change.
2. Update path: forbidden target combined with a role change; custom caller assigning examiner/employee on update (assignment table covers create only); sensitive-permission custom role on update and import; unknown `role_id` (expect 422); malformed UUID (G4).
3. Import: rejection of a peer `department_admin` row and of an `examiner` row for an examiner-level caller; commit mode asserting rejected rows write nothing (only preview is asserted); custom caller with a sensitive-permission role row.
4. Callers and targets without department on all four mutations plus create and import.
5. Deactivated (inactive) targets for reset, unlock, update.
6. Self cases: super_admin changing own role (documents G3), self-deactivate, custom caller changing own role.
7. Handler-level 403 mapping for `PUT /users/{id}`, `POST /users`, import; assertion that no e-mail is triggered on a forbidden reset (tests run with a nil e-mail service).
8. Router-level test with real RBAC (examiner token on `users:manage` routes gets 403).
9. Frontend: routed `pages/admin/users/UsersListPage` reset and unlock 403 message (G6).
